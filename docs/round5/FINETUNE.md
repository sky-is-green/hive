# LFM3 role SFT — first real run (P0)

**Date:** 2026-10-30
**Target:** `LFM3-1.7B-Base` + TRL SFT + LoRA (the Liquid recipe)
**Shipped artifact:** `work/train-runs/lfm3-role-sft-v3/`

This is the first real fine-tune of the LFM3 base checkpoint, not a smoke run.
It uses a checker-validated role corpus, holds out the 74-task role suite, and
scores base vs SFT on that suite. The ternary `--ste --rotate` recipe was **not**
used on LFM3.

## Result

Held-out role suite, 72 text tasks (2 vision tasks skipped), greedy decoding:

| model | overall | planner | controller | router | judge | mechanics | rag | risk |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| LFM3-1.7B-Base | 0.653 | 10/17 | 2/9 | 5/10 | 17/21 | 4/4 | 3/4 | 1/2 |
| SFT v1 (513 steps) | 0.750 | 11/17 | 6/9 | 5/10 | 17/21 | 4/4 | 4/4 | 2/2 |
| SFT v2 (588 steps) | 0.806 | 10/17 | 7/9 | **7/10** | **19/21** | 4/4 | 4/4 | 2/2 |
| **SFT v3 (615 steps)** | **0.833** | **13/17** | **8/9** | 6/10 | 18/21 | 4/4 | 4/4 | 2/2 |

Face (2/2) and agency (3/3) are perfect for every row, including base, and are
omitted from the width of the table.

v3 is the best overall and the best planner/controller result. Router is the
one regression against v2 (6/10 vs 7/10); all three misses are complex requests
classified as medium. That is why the live router seat stays on Scion-35B.

|---|---:|---:|---:|---:|---:|---:|

## What was trained

### Data

`experiments/build_role_sft.py` generates a synthetic role corpus and validates
**every** emitted `(prompt, answer)` pair with the same deterministic checkers
as `experiments/roles/tasks-roles.json`. Invalid pairs are dropped, so the
corpus cannot teach an answer the benchmark would reject.

v3 corpus: **3,266 rows**.

| role | rows | task shapes |
|---|---:|---|
| planner | 649 | JSON plans, capacity arithmetic, critical path, waves, drive pairs, schedules |
| controller | 517 | exact assignments, skill/release schedules, feasibility, priority |
| judge | 520 | grounding, code review, safety, format, ties, capacity, feasibility, completeness |
| router | 500 | simple/medium/complex requests, including compound multi-action work |
| mechanics | 260 | invoice totals, extraction, effective dates |
| rag | 260 | passage QA, context/card lookup, arithmetic |
| agency | 200 | tool selection and tool order |
| risk | 200 | safe/warn/block command classification |
| face | 160 | sentence/word/term constraints |

The 74 real benchmark prompts are **not** in the corpus; they are the held-out
evaluation. Artifacts are under `experiments/data/role-sft-v{1,2,3}/` (gitignored,
regenerated by the builder).

Three iterations shaped the data:

1. **v1** — broad synthetic mix. Learned format, but controller gold assignments
   were arbitrary feasible partitions, so the strict `expected_assignments`
   checker rejected valid-but-different answers.
2. **v2** — controller gold uses the benchmark's first-fit convention (fill W1
   in task order, overflow to W2/W3); router/judge/planner pools widened.
3. **v3** — controller answers carry a `loads` scratch key (checker ignores
   extras), planner number answers carry a compact calculation ending in the
   answer (the `number` checker reads the last number), more exact-fill
   controller cases, more waves/critical-path examples.

### Recipe

Liquid's LFM3 SFT notebook, unchanged where it matters:

- LoRA r=16, alpha=32, dropout 0.05, targets
  `q_proj,k_proj,v_proj,o_proj,in_proj,out_proj,w1,w2,w3`
- bf16, lr 2e-4, cosine, warmup 5%, completion-only loss
- 3 epochs, batch 8 × grad-accum 2 (effective 16), max length 512
- 615 steps, 638.7 s, peak 14.03 GiB reserved
- transformers 5.22.1, trl 0.23.1, peft 0.18.1, torch 2.11.0+rocm7.2
- 1.73B params, 16.1M trainable (0.923%)

### GPU window

Training ran on the **non-display card alone** (`HIP_VISIBLE_DEVICES=1`,
14.49 GiB free with DS4.1 resident). Scion-35B was already down after the
reboot, so it did not have to be stopped. DS4.1 stayed live throughout; the
LoRA run peaked at 14.03 GiB and left the display card free.

The v3 run loaded 19.9 GiB total on card0 including DS4.1 at points — close to
the 20 GiB limit but stable. If DS4.1 is reconfigured to use more VRAM, reduce
batch to 4 and raise grad-accum to 4.

## TRL completion-mask fix

The LFM3 tokenizer returns a `BatchEncoding` from `apply_chat_template`, so
TRL's prompt-length probe computes the mask over the whole sequence
(`len(BatchEncoding) == 2`). The first smoke trained on prompt+completion and
logged a mismatch warning for every row.

`experiments/lfm3_sft.py` now tokenizes explicitly and supplies
`input_ids` + an exact `completion_mask` with
`dataset_kwargs={"skip_prepare_dataset": True}`. Only assistant tokens
contribute to the loss; the warning is gone. Keep this when the recipe is
ported to the Training page.

## What still fails

The remaining misses are reasoning, not format:

- **Planner arithmetic.** The model still mis-packs `planner-104` (22 GB on a
  20 GB card), splits parallel waves into separate waves (`planner-106`), and
  picks the shorter critical-path branch (`planner-102`). The arithmetic trace
  helped (planner 10/17 → 13/17), but a 1.7B does not reliably compute.
- **Router boundary.** Compound requests with several actions are classified
  medium, not complex. The live router is Scion for this reason.
- **Judge arithmetic.** `judge-117` (KV-block division) and `judge-114`
  (dependency-feasibility check) are still wrong in every version.
- **Controller exactness.** Cooked assignments are feasible but occasionally
  not the benchmark's first-fit set (`controller-003`).

These are the arguments for the own-model scale-up (Qwen3.8-27B ternary) rather
than more 1.7B epochs.

## Reproduce

```sh
cd hivebench
python experiments/build_role_sft.py --out experiments/data/role-sft-v3

HIP_VISIBLE_DEVICES=1 TOKENIZERS_PARALLELISM=false \
  ~/.unsloth/studio/unsloth_studio/bin/python experiments/lfm3_sft.py \
    --model-dir ../models-hf/LFM3-1.7B-Base \
    --data experiments/data/role-sft-v3/train.jsonl \
    --out ../train-runs/lfm3-role-sft-v3 \
    --epochs 3 --batch 8 --grad-accum 2 --max-length 512 \
    --save-steps 200 --log-steps 20 --merge

HIP_VISIBLE_DEVICES=0 TOKENIZERS_PARALLELISM=false \
  ~/.unsloth/studio/unsloth_studio/bin/python experiments/eval_role_sft.py \
    --model-dir ../train-runs/lfm3-role-sft-v3/merged \
    --out ../train-runs/lfm3-role-sft-v3/eval-sft.json
```

GGUF conversion (llama.cpp b11960 source + `gguf-py` on `PYTHONPATH`):

```sh
python convert_hf_to_gguf.py ../train-runs/lfm3-role-sft-v3/merged \
  --outfile ../train-runs/lfm3-role-sft-v3/lfm3-role-sft-v3-bf16.gguf --outtype bf16
llama-quantize .../lfm3-role-sft-v3-bf16.gguf .../lfm3-role-sft-v3-Q4_K_M.gguf Q4_K_M
```

## Deployment note

The v3 GGUF was smoke-tested on a spare endpoint (`:8165`, display card) and
then stopped. The live `:8155` endpoint is still the stock LFM3 1.7B Q4_K_M;
swapping it to the SFT model is a role change and was not done without
approval. The SFT model is a candidate for `mechanics`, `rag`, and a planner
fallback; it is not a router replacement.
